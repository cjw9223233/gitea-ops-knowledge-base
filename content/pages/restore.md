## 通用原則

1. **預設在隔離環境還原**：不同的目錄、不同的 Docker Compose 專案名、不同的對外埠（例如 3300／2322），**不覆蓋正式資料**。
2. 還原前先核對校驗值，並記錄來源備份的工作 ID 與資料截止時間。
3. 還原使用 root 並保留數字 UID／GID（`--numeric-owner`）：Gitea 容器是 1000:1000、PostgreSQL 是 999。**不要**事後對整棵目錄 `chown -R`。
4. 先啟動資料庫、確認可接受連線，再啟動 Gitea。
5. 隔離還原的 Gitea 內部連結仍可能指向舊的 `ROOT_URL`；驗收時以功能為主。
6. 每個情境都要先寫下**前置條件、決策點、驗收、回退**，再動手。

## S1 誤刪儲存庫或分支

**前置**：知道要找回的專案名稱、大約的刪除時間，以及使用者要的是「整個儲存庫」還是「某分支或某次提交」。

**決策**：

- 只是分支被刪：先在 Gitea 介面確認是否可以還原已刪分支（部分情況介面會提供還原），能還原就不需要動備份。
- 整個儲存庫被刪或資料毀損：從最近一份已校驗備份，在**隔離環境**還原，取出該儲存庫再放回正式環境（不要用整份備份覆蓋）。

**步驟（概要）**：

1. 依 S3 的步驟 2–6 在隔離環境還原最近一份備份（不對外、不接正式使用者）。
2. 在隔離 Gitea 找到該儲存庫，確認內容與時間點正確。
3. 在隔離環境 `git clone`（或 `git bundle`）取出完整歷史。
4. 在正式 Gitea 以**新名稱**建立空的儲存庫，推送取出的內容；與使用者確認後再決定是否改回原名。

**驗收**：使用者確認分支、標籤、提交歷史與需要的檔案齊全；Issue／Pull Request 若在備份時間點之後新增，會遺失，需告知使用者。**回退**：新建的儲存庫可以刪除，正式其他資料不受影響；隔離環境按 S3 步驟 7 清除。

**預估耗時**：待演練。

## S2 資料庫損毀或無法啟動

**前置**：`gitea-db-1` 無法啟動或 `healthz` 失敗，日誌顯示資料庫檔案損毀或不一致。先確認不是單純的磁碟滿（見 [事件處理手冊 R6](runbook.html)）。

**決策**：

- **不要**在唯一一份資料上直接嘗試修復。先停止服務（避免進一步寫入），再把 `/home/Gitea/postgres` 完整複製一份保存。
- 損毀確認後，評估資料遺失窗口：最近一份備份到現在之間的資料會遺失（最壞約 24 小時）。

**步驟（概要）**：

1. 在隔離環境用最近備份還原並啟動（S3 步驟 2–6），確認資料庫與 Gitea 都能正常運作。
2. 與 PM 確認可接受的資料遺失，並安排維護時段與通知。
3. 在維護時段停止正式服務，保留損毀資料目錄當證據，換成已驗證的還原資料。

停止正式服務與換資料屬於中斷服務操作：

```bash-stop
cd /home/Gitea && docker compose -p gitea -f docker-compose.yml stop
```

**驗收**：資料庫啟動、`healthz` 為 pass、能登入、能 clone 與 push 測試分支、LFS 與附件可存取、Issue／Pull Request 數量與備份時間點相符。**回退**：保留的損毀資料目錄與原 Compose 設定可還原回原狀；任何一步驗收失敗就停止，恢復原目錄後再評估。

**預估耗時**：待演練。

## S3 主機毀損：在備機或新機還原

**前置**：

- 備機（或新機）有 Docker 與 Compose，磁碟空間至少為備份大小的 2 倍以上。
- 能取得最近一份**已校驗**的備份（備機 `/home/coffee/gitea-backups/<工作 ID>/`）。
- 確認**唯一寫入端**：舊主機若還活著，必須先停止，避免兩邊都在寫。

**決策**：這是切換決策，由 PM 與 Linux 管理員共同核准，見 [備份與備援](backup.html) 的決策樹。Gitea 的 `ROOT_URL` 與使用者 remote 都是 IP，切換前先決定是讓新機接手同一個 IP，還是通知所有使用者改網址。

**步驟**（以下命令在還原的目標機器執行；`<…>` 要換成實際值）：

1. 核對備份完整性：

```bash-ro
cd /home/coffee/gitea-backups/<工作 ID> && sha256sum -c SHA256SUMS
```

2. 建立隔離目錄並解壓（用 root，保留權限、ACL 與數字 UID）：

```bash-chg
sudo mkdir -p /srv/gitea-restore && sudo tar --acls --xattrs --numeric-owner -xzpf /home/coffee/gitea-backups/<工作 ID>/gitea-cold.tar.gz -C /srv/gitea-restore
```

3. 編輯 `/srv/gitea-restore/docker-compose.yml`：把對外埠改成 `3300:3000` 與 `2322:2222`（正式切換時才改回 3000／2222），資料庫維持內部。檢查語法：

```bash-ro
cd /srv/gitea-restore && docker compose -p gitea-restore -f docker-compose.yml config --quiet
```

4. 先啟動資料庫並確認可連線：

```bash-chg
cd /srv/gitea-restore && docker compose -p gitea-restore -f docker-compose.yml up -d db
```

5. 資料庫就緒後再啟動 Gitea：

```bash-chg
cd /srv/gitea-restore && docker compose -p gitea-restore -f docker-compose.yml up -d server
```

6. 驗證健康：

```bash-ro
curl --max-time 10 -fsS http://127.0.0.1:3300/api/healthz
```

7. 通過驗收後，才進行正式切換（改埠、IP 或 DNS）；若不切換，清除隔離環境：

```bash-chg
cd /srv/gitea-restore && docker compose -p gitea-restore -f docker-compose.yml down
```

**驗收**：`healthz` 為 pass；管理員與一般帳號可登入；對代表性專案 `git clone` 與 `push` 一個測試分支；LFS 檔案可下載、附件可開啟；Issue 與 Pull Request 數量與備份時間點的統計相符；組織與團隊權限正確（Read 的人不能推送）。

**回退**：步驟 7 的 `down` 只停止隔離專案，不影響其他資料；確認不再需要後再手動刪除 `/srv/gitea-restore`。正式切換時保留舊主機的資料不要覆蓋，直到新環境穩定運作並由 PM 核准。

**預估耗時**：待演練（首次演練請完整計時，並記錄每一步花費時間）。

## S4 SSD 故障（BIOS 找不到系統碟）

**前置**：先讀 [硬碟與開機排查](hardware.html)。**不要**因為想測試而反覆強制重開機；每次冷開機都是一次風險。

**決策**：

- 能開機：立即確認最近一份備機備份是否可用，並安排維護時段做完整備份與硬體檢查。
- 無法開機、SSD 時有時無：先確認備機備份有一份已校驗的最近副本；若有，可以直接走 S3，不必冒險反覆嘗試原碟。
- 需要救出原碟資料：以唯讀方式掛載（例如用 live USB 開機，`mount -o ro`），複製 `/home/Gitea`；不要在原碟上嘗試修復。

**步驟（概要）**：保全備份 → 完全關機斷電後檢查接頭、排線與電源 → 一次只更換一項 → 若換碟，依 S3 在新碟還原。

**驗收**：還原後依 S3 的驗收清單全部通過，並完成一次完整的 daily 備份與外送。**回退**：保留舊碟不要格式化，直到新環境穩定並經 PM 核准。

**預估耗時**：待演練。
