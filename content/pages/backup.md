!!! tip "白話說明"
    備份有三道關卡，成功的意義不同：**本機成功**（`SUCCESS`，檔案做好了）→ **異機成功**（`REMOTE_SUCCESS`，備機收到而且校驗通過）→ **還原成功**（真的用它把系統重建起來）。目前只做到前兩關，而且第二關是 10/5 才第一次看到成果，**第三關從來沒做過**。

## 現行備份分層

| 層級 | 內容 | 已知限制 | 資料日期 |
|---|---|---|---|
| daily 本機 | 一致性 Gitea 冷備份（`gitea-cold.tar.gz` 等） | 與系統同一顆 SSD | 2026-10-05 |
| daily 備機 | 經 SHA-256 核對的封存檔 | 10/5 備機已見完整目錄；日誌與備機校驗待核對；**9/22–10/2 曾因 SSH 失敗未外送** | 2026-10-06 |
| weekly 本機 | 系統檔案＋最近 72 小時內合格冷備份 | 不新增週六停機；Gitea 時間點是引用的 daily，不是週六當刻；**不外送** | 2026-10-03 |
| 隔離還原 | 還原 Gitea、PostgreSQL 與資料 | **尚未演練，RTO 未實測** | — |

weekly 目前缺少正式維運程式與 root crontab 的專用復原設定包；請保留變更報告與安裝套件。不要宣稱 weekly 是完整整機映像。

## 3-2-1 原則的落差

3-2-1 的意思是：**3 份**資料、**2 種**媒介、**1 份**在異地。

| 要求 | 現況 | 落差 |
|---|---|---|
| 3 份資料 | 正式資料＋本機 daily＋備機 daily | 本機 daily 與正式資料在同一顆 SSD，實質只有 2 份獨立副本 |
| 2 種媒介 | 備機也是磁碟 | 沒有離線／不同類型媒介 |
| 1 份異地 | 備機在同一個二層網段（`192.168.1.0/24`），應與主機同處一地 | **沒有異地副本** |

這不是在責怪現況，而是讓 PM 知道：一次機房事故（火災、淹水、斷電、勒索）可能同時毀掉主機與備機。

## 備機的角色：現在是「備份接收點」

!!! warning "備機不是熱備援"
    備機目前只**接收備份檔**，沒有 Gitea、沒有資料庫在跑。主機壞了，使用者**不會**自動改連備機；需要先在備機還原，再切換入口。

| 選項 | 做法 | 優點 | 缺點／成本 |
|---|---|---|---|
| **A 冷備援**（現況＋補演練） | 備機只收備份；出事時照 [還原與演練](restore.html) 的 S3 還原 | 零額外成本、最簡單 | RTO 長（要重建）；入口切換需人工 |
| **B 暖備援**（建議下一步） | 備機定期（例如每月）還原一次並驗證；平時關閉服務 | 切換步驟熟練、能持續驗證備份可用 | 需要備機容量與固定的演練時間 |
| C 熱備援 | 備機持續同步並隨時接手 | RTO 最短 | Gitea 單機架構下複雜度高、容易腦裂（兩邊都在寫），**不建議** |

**建議**：先落實 A（把還原演練做起來），穩定後升級為 B。切換決策與核准人：由 PM 與 Linux 管理員共同核准，見下圖。

{{diagram:failover-decision}}

!!! note "切換入口是目前最大的暗坑"
    Gitea 的 `ROOT_URL` 與使用者的 Git remote 都是 **IP**（`http://10.253.114.160:3000/`）。在備機還原後，使用者要改 remote，或備機必須接手同一個 IP。建議在真正需要切換之前，先導入穩定的**網域名稱**，否則切換時所有使用者與 Webhook 都要手動改網址。

## RPO 與 RTO

- **RPO**（可接受遺失多久的資料）：目前平日一天一份，**最壞約 24 小時**；週五 20:30 之後到週一 20:30 沒有新的 daily，週末最壞可達約 72 小時。9/22–10/2 因外送失敗，備機端的有效 RPO 更長。
- **RTO**（可接受中斷多久）：**尚未實測**。沒有演練，任何 RTO 數字都只是猜測。
- 討論起點（**僅供 PM 參考，不是承諾**）：RPO 24 小時、RTO 4 小時。實際目標由 PM 與使用者代表決定，再回頭調整排程頻率與備援選項。

## 保留與容量

| 項目 | 現行行為 | 建議 |
|---|---|---|
| 本機 daily | 保留最近 7 份**已外送校驗**者；失敗時不清理 | 外送失敗仍要有上限，並在日誌警示「X 份未外送」 |
| 本機 weekly | 保留最近 2 份成功者 | 每份都含完整冷備份與系統檔案，需另外量測容量 |
| 備機 | **沒有任何保留或清理策略**，只寫入 | 建議 7 日＋4 週；清理限於受管理目錄、日期格式相符、且確認更新的備份已通過校驗後才執行，先以「只列出」模式跑一週 |
| 歷史補傳 | 不會自動補傳 9/22–10/2 的未外送備份 | 評估是否補傳最近一份已校驗的備份 |

!!! warning "外送失敗時本機備份會累積"
    本機清理只會在 daily 全部成功後才執行，且只清理有 `REMOTE_SUCCESS` 的備份。外送連續失敗時，本機 `daily/` 會一直增加；過去沒有 `REMOTE_SUCCESS` 的舊備份，即使日後外送恢復，也不會被自動清理，需管理員確認後處理。

容量估算（**估算，非量測**，資料日期 2026-10-06）：

| 項目 | 數值 |
|---|---|
| 備機可用空間 | 約 199 GB |
| 單日備份大小（估） | 約 3 GiB |
| 沒有清理時可存放 | 約 60 多天（199 ÷ 3） |
| 套用「7 日＋4 週」後的穩定佔用（估） | 約 33 GiB（11 份 × 3 GiB） |

找出沒有 `REMOTE_SUCCESS` 的本機備份（唯讀）：

```bash-ro
sudo find /var/backups/gitea-maintenance/daily -mindepth 2 -maxdepth 2 -name SUCCESS -printf '%h\n'
```

```bash-ro
sudo du -sh /var/backups/gitea-maintenance/daily /var/backups/gitea-maintenance/weekly
```

## 驗收清單

**每天（5 分鐘，維運）**

- ☐ 同一次 daily 的日誌（午夜後讀 `daily.log.1`）依序有 `Services restored and health check passed`、`Remote checksum verified`、`SUCCESS daily`。
- ☐ 備機 `gitea-backups/` 的最新資料夾**沒有** `.partial` 後綴。
- ☐ `curl http://127.0.0.1:3000/api/healthz` 為 `status: pass`。
- ☐ 沒有 `recovery-required.json`。
- ☐ 本機備份容量沒有異常成長。

**每週（維運）**：在備機對最近一份抽驗校驗值（讀取量大，避開備份時段）：

```bash-ro
cd /home/coffee/gitea-backups/<資料夾名稱> && sha256sum -c SHA256SUMS
```

另確認 `weekly.log` 有 `SUCCESS weekly`，以及上面「沒有 `REMOTE_SUCCESS`」清單沒有新增。

**每季（Gitea 管理員＋Linux 管理員）**：做一次 [還原與演練](restore.html)，並更新本頁的 RTO 與狀態。

## 備份在哪裡、怎麼讀

位置、日誌與成功標記請查 [Log 與產出物](logs.html)。處理失敗請看 [事件處理手冊 R4、R5、R6](runbook.html)。先完成最新異機副本驗收，再清查歷史積壓，**不要為了騰出空間刪掉唯一的副本**。
